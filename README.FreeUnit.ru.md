## Анализ ошибок

### Динамика failure rate по времени

| Временной диапазон (сек) | Failure Rate | Состояние |
|--------------------------|--------------|-----------|
| 0–30 | 50–80% | Severe degradation |
| 30–60 | 60–90% | Severe degradation |
| 60–90 | 70–85% | Severe degradation |
| 90–120 | 70–85% | Severe degradation |
| 120–160 | 20–80% | Flapping (recovery attempts) |

### Корневые причины высокого failure rate

1. **Connection exhaustion** — `connecting` фаза в пике занимала до 13 сек, что указывает на исчерпание пула соединений
2. **Request queuing** — `blocked` фаза до 16 сек при пиковой нагрузке
3. **Server overload** — TTFB (waiting) превышала 60 секунд, что приводило к таймаутам клиента
4. **Cascade failures** — ошибки 500/503 вероятно переполняли retry-очередь k6

## Диагностика bottle-neck

### Очередь: Симптомы → Причина

| Симптом | Вероятная причина |
|---------|-------------------|
| `blocked` > 1000 мс | PHP-FPM / FrankenPHP queue overflow |
| `connecting` > 1000 мс | Конкурентные соединения к upstream |
| `waiting` > 30 сек | Slow DB queries или блокирующий I/O |
| VUS max 21 455 vs target 50 000 | k6 достиг предела и начал сбрасывать итерации |

### Итерации dropped

- **1 860 596 dropped iterations** — k6 не смог выполнить ~89% запланированных запросов
- Это означает, что реальная нагрузка на сервер была значительно ниже целевой
- Сервер не справился, k6 сбрасывал запросы на уровне engine

## Рекомендации

### Немедленные действия

1. **Мониторинг PHP-FPM/FrankenPHP status** — проверьте `pm.max_children`, `pm.start_servers`, `request_terminate_timeout`
2. **Анализ slow query log** — какие запросы занимают >1000 мс
3. **Connection pool sizing** — увеличьте max_connections в PostgreSQL
4. **Добавьте rate limiting middleware** — для graceful degradation при превышении capacity

### Среднесрочная оптимизация

1. **OPcache** — убедитесь, что opcache.enable=1 и opcache.memory_consumption достаточно
2. **Database connection pooling** — pgbouncer или аналог
3. **HTTP/2 push** или **HTTP/3** — для снижения connection overhead
4. **CDN для статики** — если home endpoint отдает статику

### Долгосрочная стратегия

1. **Горизонтальное масштабирование** — несколько app instances за load balancer
2. **Асинхронная обработка** — для heavy endpoints (очереди, workers)
3. **Benchmark endurance test** — провести 30-60 минутный тест для проверки memory leak

## Заключение

| Аспект | Оценка |
|--------|--------|
| **Устойчивость к нагрузке** | ❌ Не прошёл |
| **Максимальная пропускная способность** | ~1 500 RPS стабильно |
| **Точка деградации** | ~2 000 RPS |
| **Failure rate под нагрузкой** | 72% — критично |
| **Время восстановления** | ~10 сек после снятия нагрузки |

Тест выявил серьёзное узкое место в обработке запросов. FreeUnit не справляется с ramp-нагрузкой выше ~2 000 RPS. Необходимо профилирование PHP-кода и конфигурации инфраструктуры.
